# CLAUDE.md

Este fichero da contexto a Claude Code (claude.ai/code) para trabajar con el código de este repositorio.

## Qué es esto

App educativa (niños de 8 a 12 años) que genera una escena divertida combinando una **ubicación** + un **personaje histórico/prehistórico** (p. ej. un T-Rex simpático en un laboratorio) y deja al niño **chatear con ese personaje** mediante un pipeline RAG. **Cliente-servidor desacoplado**: una **SPA React** (Vite + TypeScript, en el navegador) habla por HTTP/REST con un backend **FastAPI**. Toda la IA pesada (generación de imagen + LLM) corre en la nube en **Replicate**; el backend se mantiene ligero (sin torch/CUDA). El índice RAG (ChromaDB) corre en local sobre CPU.

Los comentarios del código, los docstrings y el README están en **español** — sigue ese mismo idioma al editar.

## Comandos

La gestión de dependencias del backend usa **`uv`** (Hito 1): `pyproject.toml` declara las dependencias y `uv.lock` clava las versiones exactas (incluidas las transitivas, con hashes). Ese lockfile es la **fuente de reproducibilidad** ("clona y arranca"); `requirements-backend.txt` se conserva solo como *fallback sin pin* para quien no use uv.

```powershell
# Configuración inicial (Windows PowerShell)
uv sync                              # crea .venv e instala EXACTAMENTE lo del uv.lock (backend + herramientas dev)
Copy-Item .env.example .env          # luego rellena REPLICATE_API_TOKEN, DEEPL_API_KEY y ELEVENLABS_API_KEY
cd frontend-react; npm install; cd ..   # dependencias del frontend (Node 20+), una sola vez

# Arrancar backend + frontend a la vez (Windows), cada uno en su ventana
.\scripts\dev.ps1                    # o -Solo back / -Solo front

# Arrancar el backend a mano (una terminal) — sirve en http://127.0.0.1:8000, docs en /docs
uv run uvicorn backend.main:app --reload

# Arrancar el frontend a mano (otra terminal) — servidor de desarrollo Vite en http://localhost:5173
cd frontend-react; npm run dev          # redirige /api y /health al backend

# Construir/actualizar el índice RAG — OBLIGATORIO antes de que el chat funcione, y tras cualquier cambio de documentos.
# Cada ejecución borra y reconstruye la colección de ChromaDB desde cero.
uv run python -m backend.ingest

# (Opcional) descarga un artículo de Wikipedia limpio a backend/documentos/<id>/, luego reindexa
uv run python -m backend.fetch_wikipedia t-rex https://simple.wikipedia.org/wiki/Tyrannosaurus_rex

# Calidad (Hito 1): lint, formato y tests
uv run ruff check backend/ tests/       # lint (reglas E,F,I,UP,B,SIM)
uv run ruff format backend/ tests/      # formateo
uv run pytest --cov=backend             # tests + cobertura
uv run pre-commit install               # (una vez) engancha ruff + oxlint a cada commit

# Banco de pruebas / evaluación (Hito 3) — NO cambia ningún modelo/prompt, solo mide
uv run python -m evals.runner --modo completo --etiqueta baseline   # corrida completa → CSV + HTML
uv run python -m evals.runner --volcar-fixture                      # (re)genera el fixture congelado
uv run python -m evals.runner --modo retrieval-congelado           # compara generadores (lo usa H6)
```

Hay una **suite de tests con `pytest`** en `tests/`: las funciones puras de los servicios (Hito 1) más, desde el **Hito 2 (blindaje)**, concurrencia, resiliencia (reintentos), límites de subida y validación, candado de acceso, rate limit, cupo diario, endurecimiento del PIN y saneado de errores. El CI de GitHub Actions (`.github/workflows/ci.yml`) corre lint + formato + pytest (backend) y oxlint + build (frontend) en cada push/PR contra `dev`. Además de los tests, verifica a mano los cambios de IA: comprueba que `GET /health` muestra `token_configurado: true`, `deepl_ok: true` y `elevenlabs_ok: true`, y luego prueba el flujo desde la interfaz React o `/docs`.

**Logging (Hito 1).** El backend usa el módulo `logging` (ya no `print()`), configurado en `backend/logging_config.py`: formato con marca de tiempo y nivel por `LOG_LEVEL` (`DEBUG`/`INFO`/`WARNING`/`ERROR`, por defecto `INFO`). `LOG_LEVEL` controla el *detalle* de los logs y es independiente del ajuste de producto `DEBUG`. Activa `DEBUG=true` para emitir en la **consola del backend** trazas de los prompts, del razonamiento del RAG y de la voz (`[VOZ] 🎙️ STT ...` / `[VOZ] 🔊 TTS ...`); al activarlo, `logging_config.aplicar_nivel_debug()` baja el logger `backend` a nivel `DEBUG` para que esas trazas se vean (y `settings_service.set_many` lo resincroniza al cambiar `DEBUG` en caliente). `DEBUG` es un ajuste editable en caliente (`settings_service`, con valor inicial tomado del `.env`), así que también se puede activar/desactivar desde la pestaña "Sistema" del menú de configuración sin reiniciar. (Desde el Hito 4.2, mostrar las `fuentes` al niño en el chat es un flag **aparte**, `MOSTRAR_FUENTES`, ya no `DEBUG`; ver "El Evaluator" más abajo.) El botón de diagnóstico "Probar conexión" del frontend se controla aparte con `VITE_DEBUG=true` en `frontend-react/.env`.

## Arquitectura

**Dos procesos independientes.** `backend/` (FastAPI) y `frontend-react/` (SPA React) corren por separado y solo se comunican por HTTP. La única puerta de entrada del frontend al backend es `frontend-react/src/api/client.ts`; la URL del backend viene de `VITE_BACKEND_URL` en `frontend-react/.env` (en desarrollo, el proxy de Vite redirige `/api` y `/health` al backend local, así que no hace falta configurar nada).

**Capas del backend** — routers → services → config. Los endpoints de `backend/routers/` se mantienen finos: validan, llaman a un service, y mapean `ValueError` → HTTP 400 / otras excepciones → 500. Toda la lógica real vive en `backend/services/`. Los parámetros ajustables **ya no se leen como constantes congeladas de `config.py`**: pasan por `backend/services/settings_service.py`, que devuelve el valor *vigente* desde **SQLite** (con caché en memoria, invalidada al guardar) y **cae al valor por defecto de `config.py`** cuando la BBDD no tiene ningún override. Así, un cambio hecho desde el menú de configuración surte efecto en la **siguiente petición sin reiniciar**, y con la BBDD vacía la app se comporta exactamente como antes. `config.py` sigue guardando los valores por defecto (y leyendo los secretos del `.env`); el menú de configuración sin código está documentado en el README ("Decisiones de diseño") y en ARQUITECTURA.md.

**Puerta de admin (Hito 7).** Toda la zona de configuración va detrás de un **PIN de adulto** (`backend/services/admin_service.py`): el PIN se guarda *hasheado* con PBKDF2 en la tabla `settings` (clave reservada, no está en `_SPEC`, nunca se exporta), el login devuelve un token de sesión en memoria y la dependencia `requiere_admin` protege los endpoints sensibles. En `main.py` los routers `config`/`apis`/`documentos` están protegidos por completo; los routers `personajes`/`ubicaciones` solo protegen sus **escrituras** y `GET /api/voices` (los `GET` de los catálogos siguen públicos para el flujo del niño, junto con `/generate`, `/ask`, `/transcribe`, `/health`). El frontend manda el token como `X-Admin-Token` en cada petición (`client.ts`), y la pestaña Sistema ofrece cambio de PIN, **import/export** en JSON (`/api/admin/export`|`import` — ajustes + catálogos, nunca secretos) y logout; importar llama primero a `admin_service.backup_sqlite()`. Desde el **Hito 2**, el login del PIN está endurecido contra fuerza bruta (`admin_service`): retardo fijo por intento, contador de fallos **por IP** con bloqueo temporal de espera creciente (→ **HTTP 429**), y logging de los intentos.

**Blindaje operativo y del túnel (Hito 2).** El despliegue es un túnel público (ngrok/Colab), así que los endpoints del niño se protegen sin fricción (ver ADRs en `docs/decisiones/`):
- **Concurrencia.** Los endpoints que llaman a SDKs síncronos de red son `def` (no `async def`): FastAPI los ejecuta en su threadpool y el event loop no se bloquea. Los multipart siguen `async def` pero delegan el trabajo pesado con `await run_in_threadpool(...)`. Medido en `scripts/bench_concurrencia.py` (ver `docs/mediciones/H2-concurrencia.md`). **No vuelvas a poner `async def` en un endpoint que llame a código bloqueante.**
- **Timeouts + reintentos.** `services/resiliencia.py` (`reintentar()`: backoff exponencial + jitter ante 429/5xx/timeout, `config.HTTP_MAX_INTENTOS`) envuelve Replicate (vía `services/replicate_client.py`, cliente único con `timeout`) y ElevenLabs. **DeepL queda fuera a propósito**: su SDK ya hace timeout + backoff internamente (envolverlo duplicaría). Todos los timeouts/límites son constantes de `config.py` desde el `.env` (nivel de despliegue, **no** `settings_service`).
- **Límites de subida.** `routers/limites.py::leer_con_limite` corta las subidas por trozos → **HTTP 413** (imagen 10 MB / audio 5 MB / documento 20 MB, configurables). Los schemas ponen tope de longitud a los inputs públicos (`pregunta` `max_length=500` → 422).
- **Candado del túnel.** `services/acceso_service.requiere_codigo_acceso` exige la cabecera `X-Access-Code` (== `config.ACCESS_CODE`, `hmac.compare_digest`) en los endpoints que cuestan dinero (generación, chat, voz); los catálogos GET siguen públicos. `ACCESS_CODE` vacío = candado desactivado (dev). El frontend lo manda desde `VITE_ACCESS_CODE` (`client.ts`).
- **Rate limit + cupo.** `backend/ratelimit.py` (slowapi, por IP) limita chat/generación/voz. Al superarlo, `/api/ask` responde **en personaje** (200 con `origen: "LIMITE"` y `MENSAJE_LIMITE`), y generación/voz devuelven un 429 amable — nunca un 429 crudo al niño. Además `services/cuota_service.py` lleva un **tope diario de imágenes** en SQLite (tabla `uso_diario`, `MAX_IMAGENES_DIA`), comprobado antes de gastar en Replicate.
- **Saneado de errores.** `routers/errores.py`: los 500 NO filtran el mensaje del SDK — se registra el detalle completo con un `error_id` (uuid4) y al cliente le llega un mensaje genérico + ese id. Hay un handler global de `Exception` como red de seguridad.

- **Generación de imagen** (`services/generation_service.py`, `routers/generation.py`): `POST /api/generate` (ubicación predefinida, JSON) y `POST /api/generate-on-photo` (el niño sube una foto, multipart). Construye un único prompt para Replicate y devuelve la imagen en base64. FLUX schnell (por defecto) **no tiene negative prompt** — la seguridad infantil y el estilo se cuecen dentro del prompt *positivo* vía `STYLE_SUFFIX`/`FRAMING`, ajustes editables (categoría `estilo_imagen`, pestaña "General" del menú de configuración; valores por defecto sembrados desde `backend/personajes.py`). Los prompts se ordenan **de más a menos importante** (sujeto → encuadre → estilo) porque el codificador CLIP de FLUX trunca a ~77 tokens mientras que T5 lee el resto; superar `CLIP_TOKEN_LIMIT` solo genera un warning en el log, no falla.
- **Chat RAG** (`services/chat_service.py` → `services/rag_service.py`, `routers/conversacion.py`): `POST /api/ask`. Desde el **Hito 5**, el router llama a un **orquestador** `chat_service.responder`, que pide el TEXTO a `rag_service.responder` y le añade la **voz** (TTS): así `rag_service` genera solo texto y **ya no importa `voice_service`** (era la fuga de capas principal; además prepara el streaming de H8, que necesita el texto antes que el audio). Flujo de `rag_service`: **traduce** la pregunta ES→EN (DeepL) → **recupera** fragmentos de ese personaje desde ChromaDB (distancia coseno, vía el cliente único `vector_store`) → (si `RERANKER` activo) un **cross-encoder reordena** los candidatos y se queda con el top-K → el **Evaluator/Router** decide RAG vs GENERAL → **genera** la respuesta con el LLM (vía `llm_service`). Ver invariantes más abajo.
- **Capa de proveedor de LLM** (`services/llm_service.py`, Hito 5): TODA llamada al LLM pasa por aquí, para comparar proveedores cambiando config y no código (habilita H6). `completar(system, user, max_tokens, temperature, etiqueta) -> str`, `completar_streaming(...)` (esqueleto para H8) e `info()`. Despacha por el ajuste `LLM_PROVIDER`: `replicate` (por defecto, LEGACY — envuelve `replicate_client.run` con el **mismo `input` dict** de siempre, reproduce la línea base byte a byte; hay un **test de fijación** que lo pincha) y `openai` (SDK `openai` con `LLM_BASE_URL` configurable → Groq, Mistral, Gemini-compat, OpenRouter, **Ollama local**…). El modelo es el ajuste `LLM_MODEL` (default = Llama 3 de Replicate); la clave del endpoint openai-compatible es el secreto `LLM_API_KEY` (`secrets_service`). `rag_service._llamar_llm` delega aquí.
- **Cliente único de ChromaDB** (`services/vector_store.py`, Hito 5): `cliente()` (un solo `PersistentClient` en todo el backend) + `coleccion(nombre=None)` (métrica coseno, nombre = `embeddings.coleccion_actual()`). Lo usan **tanto** `rag_service` (consulta) **como** `documentos_service` (indexado). Devuelve la colección FRESCA en cada llamada (sin objeto-colección cacheado), así que un reindexado global que borra/recrea la colección ya no deja handles obsoletos → **se eliminó `rag_service.reiniciar_coleccion()`** y su clase de bug.
- **Ingesta / documentos** (`services/documentos_service.py`, `routers/documentos.py`): la base de conocimiento del RAG se gestiona ahora **desde la UI de configuración** (Personajes → Documentos, un visor completo dentro del modal de edición) — `GET .../documentos` (lista), `POST .../documentos` (sube uno o varios ficheros `.pdf/.txt/.md` de golpe, multipart; con uno solo responde `{"documento": ...}`, con varios `{"documentos": [...], "errores": [...]}` en modo mejor-esfuerzo), `POST .../documentos/url` (URL de Wikipedia, envuelve `fetch_wikipedia`), `GET`/`PUT .../documentos/{doc_id}/contenido` (ver/editar el texto — los `.pdf` no son editables in-place), `GET .../documentos/{doc_id}/descargar` (fichero original tal cual), `POST .../documentos/{doc_id}/copiar` (copia independiente a uno o varios personajes destino; editar/borrar la copia nunca afecta al original), `DELETE .../documentos/{doc_id}`, `POST .../reindex` (por personaje), `POST /api/reindex` (global) y `GET /api/reindex/estado` (progreso del reindexado global en curso, para la barra del frontend). Un nombre de documento repetido para el mismo personaje se señaliza con `ConflictoDocumentoError` → **HTTP 409** (no 400), para que el frontend pueda ofrecer "¿sobrescribir?" de forma fiable en vez de tratarlo como cualquier otro error de validación. Los ficheros viven en `backend/documentos/<personaje_id>/`; las filas de metadatos en la tabla `documentos`. Al guardar (subida, ingesta por URL o edición de contenido), el idioma se **detecta automáticamente vía DeepL** — la propia llamada de traducción devuelve `detected_source_lang`, no hay un endpoint de detección aparte — y el texto se traduce a inglés (por lotes para documentos largos) siempre que no lo esté ya. Ya no existe la marca manual "ya está en inglés": cualquier idioma que DeepL reconozca (no solo español) se traduce automáticamente, y el nombre de fichero guardado lleva como sufijo el idioma detectado (`_en`, `_es`, `_fr`, …) para que el origen sea visible sin abrir el fichero. El reindexado es **incremental**: cambiar los documentos de un personaje solo reconstruye *sus* fragmentos (`collection.delete(where={"personaje_id": id})` + reindexar esa carpeta), nunca los de los demás; un reindexado global borra y recrea toda la colección (con el cliente único de `vector_store`, sin handles cacheados que invalidar). `backend/ingest.py` (el CLI independiente `python -m backend.ingest`) sigue haciendo un reindexado completo pero ahora **delega en `documentos_service`** (única fuente de verdad para leer/trocear/indexar). El chunking lo elige el ajuste `CHUNKING` (Hito 4.2): `recursivo` = `RecursiveCharacterTextSplitter` por tamaño (`CHUNK_SIZE`/`CHUNK_OVERLAP`); `estructura` = trocea los `.md` por secciones de Markdown (`MarkdownHeaderTextSplitter`) y guarda la ruta de encabezados en el metadato `header_path` (los `.txt`/`.pdf` caen al recursivo). Cada fragmento se etiqueta con `personaje_id`, `source` y `header_path`. **La ruta NO se prefija en el texto embebido** (medido: empeora el recall — ver ADR-005); solo alimenta la procedencia del chat. Cambiar `CHUNKING` o `EMBEDDING_BACKEND` exige reindexar (`requires_reindex`).
- **Voz** (`services/voice_service.py`, `routers/transcription.py`): `POST /api/transcribe` (audio→texto) alimenta el `/api/ask` ya existente; `/api/ask` ahora también devuelve `audio_base64` (la respuesta con la voz de ElevenLabs Flash usando el `voz_id` del personaje, de `VOCES`). ElevenLabs es el tercer proveedor (junto con Replicate y DeepL). Los fallos de voz degradan a solo-texto (`audio_base64: null`) y nunca rompen el chat. En el frontend, la grabación/reproducción usa las APIs nativas del navegador, sin librerías extra: `MediaRecorder` (`getUserMedia`) captura el micro (webm/opus en Chrome, ogg/opus en Firefox — ambos aceptados por Scribe y por faster-whisper, que deducen el formato de los propios bytes), y el `Audio()` estándar reproduce el mp3 (`data:audio/mpeg;base64,...`). `getUserMedia` solo funciona en contextos seguros (https o localhost); si no está disponible o el niño deniega el permiso, el micro se deshabilita con un aviso claro y el chat de texto sigue funcionando. **Tras transcribir, NO se auto-envía (Hito 7):** el texto entra en el input editable y aparece un **"¿has dicho esto?"** con confirmar/repetir antes de mandarlo a `/api/ask` (todos los ASR fallan con voces infantiles; confirmar es más barato que responder a la pregunta equivocada). — **STT seleccionable (Hito 7):** la transcripción pasa por `services/stt_service.py` (patrón calcado de `llm_service`), que despacha por el ajuste `STT_PROVIDER`: `elevenlabs` (por defecto, Scribe en nube, línea base) | `local` (**faster-whisper**, CTranslate2/ONNX **sin torch**, la voz del niño NO sale del PC — motivación de RGPD; dependencia OPCIONAL, extra `stt-local`, import perezoso) | `groq` (Whisper en Groq, endpoint openai-compatible, clave `GROQ_API_KEY`). `voice_service.transcribir` queda como puerta pública (router y tests intactos) y delega. **Fallback automático:** si el STT local no carga (paquete ausente, o DLLs de cuBLAS/cuDNN que faltan en Windows) o falla, `stt_service` avisa por `logger.warning` y cae a la nube — la app nunca se queda muda. El default `elevenlabs` reproduce la línea base (un clon limpio arranca sin CUDA); `local` es la config recomendada que se activa en caliente. Ajustes: `STT_PROVIDER`/`STT_LOCAL_MODEL`/`STT_LOCAL_DEVICE`/`STT_LOCAL_COMPUTE`/`GROQ_STT_MODEL` (categoría voz, `settings_service`); `GROQ_API_KEY` es un secreto (`secrets_service`, proveedor `groq`). La comparativa de proveedores por **WER** está en `evals/stt.py` (ADR-008).
- **Menú de configuración** (`services/settings_service.py` + `services/secrets_service.py`, `routers/config.py` + `routers/apis.py`): dos responsabilidades separadas detrás de la misma puerta de PIN. `GET`/`PUT /api/config` lee/escribe los ajustes editables en caliente (`settings_service`, ver arriba) y siempre devuelve las claves de los proveedores **enmascaradas**. `GET`/`PUT /api/apis` + `POST /api/apis/{proveedor}/test`|`reveal` gestionan los secretos propiamente dichos — `secrets_service.py` lee/escribe el `.env` de forma atómica (fichero temporal + backup) y nunca devuelve una clave completa salvo en la llamada explícita `/reveal`. Mantener los secretos fuera de `settings_service`/SQLite por completo es deliberado: `GET /api/admin/export` (import/export JSON, pestaña Sistema) vuelca ajustes + catálogos pero nunca debe filtrar claves API.
- **Diálogos bloqueantes en la UI de configuración** (`frontend-react/src/components/Modal/Modal.tsx`): componente genérico (portal + backdrop, cabecera sticky con el título fijo) reutilizado por la edición de personajes (`PersonajesTab.tsx`, título `Editando: <nombre>` fijo aunque se haga scroll por el panel de documentos) y por el reindexado global. Su prop `bloqueado` añade una segunda capa: mientras una operación no interrumpible está en curso (subir/traducir/reindexar un documento, reindexar todo), ni el botón "✕", ni el backdrop, ni Escape cierran el modal, y se pinta un overlay con spinner (más una barra de progreso opcional, alimentada por sondeo real de `GET /api/reindex/estado` para el reindexado global, no simulada). El mensaje se centraliza en `MENSAJE_PROCESANDO` para que cualquier indicador de carga de la pantalla de configuración diga lo mismo.

`backend/routers/_future_phases.py` ya no existe — la entrada de voz, planeada en su día con Whisper, se lanzó finalmente con ElevenLabs (ver arriba).

## Invariantes críticos

- **`personaje_id` es una clave transversal.** Desde el menú de configuración (Hito 4), el catálogo de personajes vive en la **tabla SQLite `personajes`** (columnas `nombre`, `categoria`, `emoji`, `prompt_imagen`, `voz_id`, `activo`, …), leída a través de `backend/services/personajes_service.py` y consumida **tanto** por el backend (generación de imagen + chat RAG) como por el frontend **vía `GET /api/personajes`** — el frontend ya no guarda un catálogo estático. `backend/personajes.py` es ahora solo la **fuente de "seeding"** (`PROMPTS`/`NOMBRES`/`VOCES`/`CATEGORIAS`/`EMOJIS`, más los valores globales por defecto de `STYLE_SUFFIX`/`FRAMING` — los valores *vigentes* son ajustes de `settings_service`, categoría `estilo_imagen`), volcada a la tabla en el primer arranque (`seed.py`, idempotente + backfill). Crear un personaje desde la pestaña Personajes (`POST /api/personajes`) escribe la fila **y** crea su carpeta `backend/documentos/<personaje_id>/` para el RAG. Así, el único sitio que aún se edita a mano para un personaje es esa carpeta de documentos; `voz_id` (una voz de ElevenLabs) sigue siendo opcional (sin voz = solo texto). El catálogo tiene un tope de `MAX_PERSONAJES` (`config.py`, 10 por defecto, desde `.env`) — un límite fijo de despliegue, **no** expuesto vía `settings_service`/la UI de configuración; `personajes_service.crear` lanza `ValueError` (→ 400) al alcanzar el tope (activos + inactivos), y `GET /api/personajes` lo devuelve como `limite` para que el frontend pueda deshabilitar "Nuevo personaje" proactivamente. **Las ubicaciones funcionan igual ahora** (Hito 6): el catálogo vive en la **tabla SQLite `ubicaciones`** (`nombre`, `emoji`, `prompt`, `activo`), leída a través de `backend/services/ubicaciones_service.py`, consumida por el backend (generación) y el frontend vía `GET /api/ubicaciones` (CRUD en `POST/PUT/DELETE /api/ubicaciones`); `backend/ubicaciones.py` es ahora solo la fuente de "seeding" (`UBICACIONES`/`NOMBRES`/`EMOJIS`) y el antiguo `frontend-react/src/data/ubicaciones.ts` se eliminó.
- **Entra en inglés, sale en español.** La base de conocimiento, todas las consultas de recuperación y todos los prompts al LLM (`system`+`user` de RAG, GENERAL y el juez del Evaluator) están en **inglés** — Llama 3 sigue mejor las instrucciones en inglés y los embeddings puntúan mejor en inglés. Solo se traduce la *pregunta* del niño (ES→EN vía DeepL en tiempo real); la *respuesta* se genera directamente en español por instrucción del prompt. Los prompts de sistema/usuario son **ajustes editables** (los valores por defecto viven en `settings_service.py`, externalizados de `rag_service.py`, con placeholders `{nombre}`/`{fichas}`/`{pregunta}` rellenados por sustitución literal); están en inglés por defecto y **no** se traducen en tiempo real.
- **DeepL es obligatorio para el chat Y para gestionar documentos del RAG.** Sin él, la recuperación trae los fragmentos equivocados. `translation_service.traducir_es_en` lanza `TranslationError` (un `ValueError` → HTTP 400) en lugar de degradar en silencio. La gestión de documentos (subida, ingesta por URL, edición de contenido) también exige DeepL sin condiciones — `translation_service.traducir_a_ingles` (usado para la detección automática de idioma, ver arriba) se llama en **cada** guardado, incluso para documentos ya en inglés, así que no hay forma de añadir/editar un documento sin DeepL configurado. El hook de arranque de `main.py` avisa si DeepL no está accesible pero no bloquea el servidor (así `/docs` y `/health` siguen disponibles).
- **Hay que indexar antes de chatear.** `rag_service` solo *lee* la colección de ChromaDB; nunca la construye. Una colección vacía registra un warning y da respuestas pobres. Gestionar documentos desde la UI de configuración **reindexa automáticamente** el personaje afectado; el CLI `python -m backend.ingest` sigue haciendo una reconstrucción completa tras cambios de documentos fuera de la UI.
- **ChromaDB usa distancia coseno** (`hnsw:space: "cosine"`, 0=idéntico … 2=opuesto), configurada de forma idéntica en `documentos_service` (indexado) y `rag_service.py` (consulta). Los umbrales `EVALUATOR_UMBRAL_BAJO`/`ALTO` del Evaluator dependen de esta métrica **y del backend de embeddings** (cada modelo da distancias en su escala; al cambiar `EMBEDDING_BACKEND` hay que recalibrar los umbrales — ver ADR-004).
- **El backend de embeddings es seleccionable (Hito 4).** `services/embeddings.py` + el ajuste `EMBEDDING_BACKEND`: `minilm-en` = original (all-MiniLM-L6-v2, monolingüe inglés, colección `documentos_en`, delega en la embedding_function de Chroma → requiere traducir la pregunta con DeepL); `multi-minilm` / `e5-large` = multilingües locales vía **`fastembed`** (ONNX/CPU, sin torch) que **embeben el español directamente** (embeddings manuales: `embed_passages` al indexar, `embed_query` al consultar) en su colección versionada propia. `minilm-en` reproduce la línea base; cambiar de backend **exige reindexar** (`requires_reindex`) y **recalibrar los umbrales con el runner**. `documentos_service` (indexado) y `rag_service` (consulta) ramifican por `embeddings.usa_manuales()`.
- **El reranker es un cross-encoder opcional (Hito 4.3).** `services/reranker.py` + el ajuste `RERANKER` (`off` por defecto | `jina-v2` = `jinaai/jina-reranker-v2-base-multilingual`, vía **`fastembed`**, ONNX/CPU, sin torch). Con reranker activo, `rag_service._recuperar_contexto` recupera `RERANK_CANDIDATOS` candidatos (embudo, def. 5), el cross-encoder los **reordena por relevancia** (lee pregunta+ficha juntas, más fino que el coseno) y se queda con `RAG_TOP_K`. Reordena **en consulta**, así que **NO exige reindexar** (a diferencia de `EMBEDDING_BACKEND`/`CHUNKING`) — se activa en caliente. Con reranker, el Evaluator **decide el ruteo por la puntuación del cross-encoder** (`rerank_score ≥ RERANK_UMBRAL ⇒ RAG`, método `rerank`), lo que **sustituye al LLM-juez** y deja inactivos `EVALUATOR_MODE`/los umbrales coseno; sin reranker, todo el camino coseno de siempre intacto. La puntuación es un logit (más alto = más relevante, puede ser negativo) y va en sentido CONTRARIO a la distancia coseno. Config recomendada de H4 (medida, ADR-006): `jina-v2` + candidatos 5 + umbral −2,75. El default `off` reproduce la línea base.
- **El umbral del RAG se expone y se guarda como la distancia coseno directa (0–2), nunca como porcentaje.** La UI de configuración edita `EVALUATOR_UMBRAL_BAJO`/`ALTO` directamente como floats en `[0, 2]` (paso 0.01, validando `0 ≤ BAJO ≤ ALTO ≤ 2`). **No** añadas ninguna conversión `(1 − d/2) × 100` ni una etiqueta de "% de similitud" — el valor que configura el adulto debe ser exactamente el que usa el motor, y se compara contra la `d=...` real que se muestra en `/api/ask` y en la consola con `DEBUG`.

## El Evaluator (decisión RAG vs GENERAL)

`rag_service._decidir_origen` decide si una respuesta está fundamentada en los fragmentos recuperados (`origen: RAG`) o si cae al conocimiento propio del modelo (`origen: GENERAL`). Se controla con `EVALUATOR_MODE` (un ajuste editable en caliente vía `settings_service`; valor por defecto desde el `.env`):

- `umbral` — solo umbrales de distancia, sin llamada extra al LLM (gratis).
- `llm` — una llamada al LLM "juez" responde SÍ/NO cada vez (más listo, cuesta una llamada).
- `hibrido` (por defecto/recomendado) — los umbrales resuelven gratis los casos claros; el LLM-juez solo desempata en la banda ambigua entre los dos umbrales.

**Con el reranker activo (`RERANKER != off`, Hito 4.3) esto queda anulado:** el ruteo lo decide la **puntuación del cross-encoder** (`rerank_score ≥ RERANK_UMBRAL ⇒ RAG`, método `rerank`), no `EVALUATOR_MODE` ni los umbrales coseno, y **el LLM-juez ya no se llama** (el reranker hace su trabajo, mejor y sin una llamada de red). Ver ADR-006.

Calibra `EVALUATOR_UMBRAL_BAJO`/`ALTO` ejecutando con `DEBUG=true` y leyendo las distancias `d=...` que se imprimen por cada pregunta.

**El desplegable "📚 ¿De dónde lo he sacado?" del chat** (`frontend-react/src/components/Chat.tsx`, un `<details>` que se muestra cuando un mensaje trae `fuentes` no vacías) se controla desde el **Hito 4.2** con su **propio** flag `MOSTRAR_FUENTES`, ya **no** con `DEBUG`. En `rag_service.responder`, la rama RAG hace `fuentes = [...] if settings_service.get("MOSTRAR_FUENTES") else []`, anteponiendo a cada ficha su ruta de encabezados (`[Sección] …`, vía `_formatear_fuente`) para dar procedencia real. La respuesta se genera igual a partir de los fragmentos del RAG en ambos casos; `MOSTRAR_FUENTES` solo decide si el niño *ve* qué fragmentos se usaron. Enseñar la procedencia es pedagogía, no depuración: por eso es un flag aparte de `DEBUG` (que ya solo controla las trazas de consola del backend).

**`EVALUATOR_MODE` solo controla cómo se decide el reparto RAG/GENERAL — por sí solo no detiene las llamadas externas.** Cada pregunta llama siempre a DeepL (traducción) y, una vez decidido el reparto, exactamente una vez al LLM de Replicate para generar la respuesta final (el prompt de RAG con fichas, o el de GENERAL sin ellas) — `umbral` solo se salta la llamada *extra* del juez, no la llamada de generación de la respuesta. Para conseguir de verdad una respuesta con cero llamadas al LLM cuando las fichas no cualifican, hay un ajuste ortogonal: `PERMITIR_CONOCIMIENTO_GENERAL` (`config.py`, editable en caliente vía `settings_service`, categoría `rag`). Cuando está en `false`, `rag_service.responder` toma un tercer camino (`origen: "SIN_INFO"`) en vez de GENERAL: devuelve el ajuste fijo y editable `MENSAJE_SIN_INFORMACION` (categoría `prompts`, texto plano en español, sin `{fichas}`/`{pregunta}` — `{nombre}` opcional) sin llamar al LLM en absoluto. El TTS se sigue ejecutando sobre ese texto fijo si el personaje tiene voz (eso es ElevenLabs, no tiene relación con el ahorro de llamadas al LLM).

## Banco de pruebas / evaluación (Hito 3)

El paquete `evals/` es el **instrumento de medida** del sistema (ver `docs/EVALUACION.md` y el ADR-003). No cambia ningún modelo/prompt/proveedor: solo mide, para que a partir de H4 los cambios se defiendan con números y no con opiniones.

- **Sets** (YAML, validados con Pydantic en `evals/esquema.py`): `set_dorado.yaml` (100 preguntas de calidad, 20 por personaje activo, en **español infantil real** con faltas, distribución 6 literal / 5 inferencial / 4 fuera_dominio / 3 sin_respuesta / 2 ambigua, con `chunk_esperado` para recall@3) y `set_seguridad.yaml` (18 adversariales: muerte/violencia/miedo/salir del papel/datos personales/inyección; el tacto se juzga a mano). `evals/adversarial/doc_inyeccion.md` es una ficha con inyección de prompt **preparada para H9** (no se ingiere).
- **Runner** (`evals/runner.py`): orquesta el pipeline por etapas **reutilizando `rag_service` sin tocarlo** (traducción → retrieval → Evaluator → generación), mide latencia por etapa, **salta el TTS**, y corre cada pregunta 3× a `temperature=0` (media ± σ). Dos modos: `completo` (mide el sistema) y `retrieval-congelado` (lee `evals/fixtures/retrieval_*.json` y solo evalúa+genera, para comparar generadores en H6 sin ruido del retriever). Salidas: CSV + HTML + resumen por consola en `evals/resultados/` (gitignored salvo `BASELINE.csv`/`.html`).
- **Métricas deterministas** (`evals/metricas.py`, sin juez LLM): acierto de **ruteo** (RAG vs no-RAG, no el string exacto de origen), **recall@3**, distancia, idioma (`lingua`, offline), longitud, **legibilidad INFLESZ/Fernández Huerta** (a mano con `pyphen`, objetivo INFLESZ ≥ 80 "muy fácil"; se descartó `textstat` por arrastrar nltk/regex), y "roto de personaje" (regex de fugas tipo "como IA"). Reproducibles (tests en `tests/test_evals.py`).
- **Línea base** (`evals/resultados/BASELINE.csv`, **inmutable/solo lectura**): el punto de referencia congelado contra el que se compara todo cambio posterior. La config con la que se generó se archiva en cada corrida.
- **Estudio de LLMs (Hito 6)** — sobre el runner (modo `retrieval-congelado`, retrieval congelado para todos), la maquinaria que **elige el LLM generador** con método defendible: **puertas primero, pesos después** (ver ADR-007). `evals/candidatos.yaml` declara los 5 candidatos (Llama 3/Replicate = línea base, Gemini Flash, Mistral Small, Groq 70B, Ollama local) + el juez con su config exacta; `evals/comparar.py` agrega las 5 corridas y aplica las **puertas §8** (idioma ≥98 %, INFLESZ **media ≥ 68** —calibrada sobre la línea base, no el ≥80 del doc, que queda como objetivo de mérito—, longitud 15–90, p95 ≤ 8 s, seguridad 0 fallos) y luego los **pesos §7** (calidad 50 / latencia 30 / coste 20), **fijados como constante FECHADA en el código** (2026-08-02, antes de ejecutar); `evals/juez.py` es el juez LLM de **fidelidad al contexto** (modelo distinto y más potente que los candidatos, **validado** contra 20 respuestas a mano, acuerdo ≥85 % o se descarta); `evals/test_ciego.py` genera pares **anonimizados+aleatorizados** entre los 2 finalistas y agrega los votos humanos. Los inputs de juicio (seguridad, juez, ciego) se rellenan a mano en `evals/resultados_h6.yaml`. La **clave del endpoint openai-compatible es una sola** (`LLM_API_KEY`): comparar proveedores de pago exige cambiarla en el `.env` antes de cada corrida (Replicate usa su `REPLICATE_API_TOKEN`; Ollama no pide clave). Todas las piezas puras tienen tests en `tests/test_h6.py` (ninguno llama a un LLM).
